# 4. Database Design

## 4.1 Overview

MaintenX uses **PostgreSQL**, accessed through **Entity Framework Core** with the Npgsql
provider. The schema is code-first: entity classes and `AppDbContext` define it, and **18 EF Core
migrations** build it. It has **15 tables** in six groups (Figure 4.1).

![Figure 4.1](diagrams/er-diagram.png)

*Figure 4.1 — ER diagram: 15 tables, 23 foreign keys, grouped by business component.*

## 4.2 Entities and relationships

| Group | Tables | Purpose |
|---|---|---|
| Identity and estate | `Users`, `Buildings`, `Rooms` | Accounts and roles; the campus estate |
| Asset registry | `AssetCategories`, `Assets`, `ServiceRecords` | Equipment, QR tags, and the permanent repair history |
| Reporting and clarification | `Reports`, `ClarificationQuestions`, `ClarificationAnswers` | Faults and the agent's bounded questions and answers |
| Agent workflow state | `AgentWorkflows`, `AgentSteps` | Each agent run: objective, plan, state, outcome, and every step with its time, retries and tokens |
| Work orders and scheduling | `WorkOrders`, `ScheduledSlots`, `ClassScheduleSlots` | Repairs, approvals, booked visits, and the mirrored timetable |
| Verification | `VerificationChecks` | Whether a repair held: the reporter's answer and the agent's opinion |

**Key relationships:** a building has many rooms; a room has many assets; an asset has many
service records, reports and work orders. A report has its workflows (one per agent run),
clarification questions and work orders. A workflow has many steps. A question has **at most one answer**
(one-to-one). A work order has many booked slots and verification checks, and links to its
assigned technician and approving manager.

**Delete rules.** There are 23 foreign keys:

- **Restrict (19 keys)** wherever history must survive. Deleting an asset, report, work order or
  user that is referenced fails, rather than silently removing its history. Assets are
  **retired** and users **deactivated** instead.
- **Cascade (4 keys)** only where a row means nothing without its parent: a building's rooms, a
  workflow's steps, a question's answer, and a work order's booked slots.

**Optional links, and why:**

| Foreign key | Why it can be null |
|---|---|
| `Reports.AssetId` | A reporter may not know the asset |
| `ServiceRecords.WorkOrderId` | Imported or seeded history has no work order |
| `WorkOrders.AssignedTechnicianId` | Not set until a manager assigns someone |
| `WorkOrders.ApprovedByUserId` | Not set when the order was auto-approved |
| `AgentWorkflows.ReopenedWorkOrderId` | Set only when a repair is reopened |

## 4.3 Normalisation

The schema is in **third normal form (3NF)**: each table describes one entity, every non-key
column depends on the whole key, and there are no transitive dependencies. For example, a room's
building is stored on `Rooms`, not repeated on `Assets`. Three deliberate exceptions:

| Exception | Reason |
|---|---|
| `ServiceRecords.TechnicianName` is text, not a foreign key | History records the name as it was at the time, and imported history has no user account |
| `VerificationChecks.AssetId` repeats the work order's asset | The sweep and the metrics read checks by asset without a join |
| `AgentSteps.PayloadJson` stores the agent's reply as JSON | It is an unedited audit copy, not working data; the working data (questions, verdicts) is in normal columns |

## 4.4 Data types

| Data | PostgreSQL type | Why |
|---|---|---|
| Money (estimate, actual cost) | `numeric(18,2)` | Exact to the cent. A floating-point value could fall just under the approval threshold |
| Calendar dates (installed, warranty, serviced) | `date` | A date cannot shift by a day across time zones |
| Moments in time | `timestamptz` (UTC) | Unambiguous; displayed in campus time |
| Plans, tool payloads, options, evidence | `jsonb` | Structured agent data, validated as JSON by the database |
| Enums (role, statuses, strategy) | `varchar(50)`, stored by **name** | Readable in queries; adding an enum member cannot re-label old rows |
| Identifiers | `integer` identity | Generated by the database |

## 4.5 Constraints and indexes

**Constraints:**

- **Primary keys** on every table, and **foreign keys** as above.
- **NOT NULL** and maximum lengths on every required column.
- **6 unique indexes:**
  - user email;
  - building code;
  - category name;
  - asset tag, which is the QR payload, so one scan must find exactly one machine;
  - the Google Calendar event id, so a timetable re-sync updates rows instead of duplicating them;
  - one answer per clarification question.
- **4 CHECK constraints:**
  - the estimated cost is never negative;
  - the actual cost is never negative (or not yet recorded);
  - a booked visit ends after it starts;
  - a timetabled class ends after it starts.

The API validates the same rules first and returns a 400 or 409. The database is the final
safeguard for any writer that skips the API.

**Indexes.** There are 35, each serving a real query:

- every foreign key, for joins and filters;
- the list filters and sorts (report status and date, work order status, workflow state);
- `ServiceRecords.ServicedOn`, for history read as a time series;
- the timetable's room and start time, for slot conflict checks;
- a **composite index on `VerificationChecks (Status, DueAt)`** for the verification sweep's
  query, "pending checks that are now due". `Status` comes first because it is the equality
  test, which lets the same index also answer "all pending checks".

## 4.6 Migrations

All 18 migrations run, in order, against a fresh PostgreSQL 16 database in CI on every push,
so a broken migration fails the build.

| Migrations | What they add |
|---|---|
| `InitialCreate`, `AddAgentWorkflows`, `AddReports` | Users, estate, workflows and steps, reports |
| `AddAssetRegistry`, `AddClarificationPersistence` | Assets, service history, questions and answers |
| `AddWorkOrders`, `AddWorkOrderRevisionNote`, `AddWorkOrderSlaDueAt` | Work orders, slots, timetable, revision note, SLA |
| `AddVerification`, `AddVerificationSweep`, `AddVerificationAgentEvidence`, `AddVerificationAgentRun` | Verification checks and the agent's review |
| `AddReportQueryIndexes`, `AddWorkflowReopenedWorkOrder`, `AddAgentStepAttempts`, `AddAgentStepTokenUsage` | Query indexes, the reopen link, retry counts, the tokens each agent run used |
| `AddMoneyAndSlotCheckConstraints`, `AddUserIsActive` | CHECK constraints; account deactivation |

Migrations that tighten the schema **repair existing data first**. `AddReports` and
`AddWorkOrders` clear orphaned ids before adding a foreign key. `AddMoneyAndSlotCheckConstraints`
fixes invalid rows before adding its checks. `AddUserIsActive` defaults existing users to active.
`AddAgentStepTokenUsage` only adds two nullable columns and backfills nothing: earlier runs
reported no tokens, and an empty value says so, where a zero would claim they were free.
CI migrates an empty database, so without these steps a migration could pass CI and still fail on
a database that already holds data.

## 4.7 Transactions

| Operation | What must happen together |
|---|---|
| Filing a report | The report and its workflow, so no report is left without an agent run |
| Completing a job | The order completed, a service record appended, the workflow moved, a verification check raised |
| An approval decision | The order claimed with a conditional update (so two managers cannot both decide), then its status, the workflow move and the audit step |
| Booking a slot | The conflict re-check and the insert, at `Serializable` isolation, so two managers cannot book the same technician at once |

## 4.8 Audit fields and data minimisation

Every table has `CreatedAt` and `UpdatedAt`, stamped automatically in UTC on every save, so no
code has to remember to set them. The timetable also keeps `SyncedAt` (last confirmed by Google)
separate from `UpdatedAt` (last changed).

**Not stored:** plain-text passwords (only a salted hash), tokens, API keys, image bytes (only a
storage URL), or hidden model reasoning. Agent tool results leave out names and reporter ids.

## 4.9 Seed data

In development, the database is seeded with 2 buildings, 6 rooms, 4 categories, 8 assets,
14 service records, one account per role, completed and live work orders, and verification
checks. Projector `PRJ-MAB101-01` carries a deliberately planted **repeat-failure history**
(three visits in four months for the same thermal fault). That pattern appears only in the
technicians' notes, which is what the diagnostic agent has to find.
