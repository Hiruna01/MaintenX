# 6. Third-Party Integrations

MaintenX integrates three external services. The two business integrations, **Google Calendar**
and **Supabase Storage**, are reached **only through the ASP.NET Core API**: the clients never
hold their credentials. The third, the **LLM provider**, is reached only by the internal agent
service. All three are used on free tiers.

| Service | Business purpose | Called from | Credential |
|---|---|---|---|
| Google Calendar API | Mirror the campus timetable so repairs are never booked during a class | API | Google service account (read-only) |
| Supabase Storage | Store report photos and repair-completion photos | API | Service-role key |
| LLM provider (OpenAI-compatible; OpenRouter in development) | Model inference for the five agents | Agent service | API key |

---

## 6.1 Google Calendar: the campus timetable

**Purpose and user benefit.** A technician arriving in the middle of a lecture disrupts teaching
and wastes the visit. The campus timetable is kept in a Google Calendar ("Campus Timetable"), and
MaintenX mirrors it into its own `ClassScheduleSlots` table. The slot finder then offers only
times that avoid every class in the room, with a 15-minute buffer either side, inside working
hours, and without clashing with the technician's other visits.

**How it works.**

- **Access** is by a **Google service account**, never a user's OAuth login. The calendar is
  shared read-only with the service account, and the only scope requested is
  `calendar.readonly`.
- **Sync schedule:** a background worker syncs at startup and every 60 minutes. A Facilities
  Manager can also press "Sync timetable now". The window is the next 180 days.
- **Matching:** an event becomes a class when its location matches a room code exactly. Events
  with no matching room, all-day events and events without times are **skipped and logged,
  never guessed**.
- **Upsert:** each event's Google id is a unique key, so re-syncing updates rows rather than
  duplicating them.
- **Deletion:** a class is removed only when Google reports it cancelled, or when it moves to a
  location that is not one of our rooms. It is never removed just because it was absent from a
  reply. A missing class would make the room look free, which is the dangerous direction.

**Failure handling.**

| Situation | Handling |
|---|---|
| Timeout | One 10-second limit over the whole fetch. The client library's automatic retry is switched off so it cannot use up that time; the next scheduled sync is the retry |
| Google unavailable (5xx), unreachable, or an invalid response | The sync reports `degraded: true` with a reason by name (`GoogleServerError`, `Unreachable`, …) and **leaves the existing timetable untouched** |
| Rate limit (429, or a 403 for a quota) | Reported as `RateLimited`, with Google's `Retry-After` value when it sends one |
| Bad credentials, calendar not shared | `AuthenticationFailed` or `Rejected`; logged, never a server error |
| Not configured | The API still starts and reports `NotConfigured` |
| Stale data | Every response shows the cache's age. Older than 24 hours adds a warning |

**The key design decision:** the slot finder **reads only the local copy and never calls Google**.
A Google outage therefore makes the timetable less fresh, but never stops scheduling. Only one
sync runs at a time.

**Data minimisation.** Nothing is sent to Google except the calendar id and time window. Only an
event's id, title, room and times are stored.

**Evidence.** Verified live on 30 September 2026 against the real Calendar API. 232 classes were
synced with none skipped. The slot finder offered only times around that day's lectures and
their buffers. With a wrong calendar id, the sync reported `degraded` / `Rejected` and the same
slots were still offered from the cache.

## 6.2 Supabase Storage: photos

**Purpose and user benefit.** A photo shows the technician what the reporter saw, before the
visit. A completion photo records what the repair looked like when it was finished.

**How it works.**

- **Uploads go through the API**, never directly from a client, so the Supabase service-role key
  exists only in the API's configuration.
- **Photos are checked before upload:**
  - only JPEG or PNG, up to 5 MB;
  - the file's first bytes must match its claimed type (a magic-byte check), because the content
    type is just a header the client wrote.
- **The object name is generated by the server**: a random GUID plus the extension. The client's
  file name is never read, which rules out path-traversal attacks.
- **Only the photo's URL** is stored in PostgreSQL, never the image bytes.

**Failure handling.**

| Situation | Handling |
|---|---|
| Timeout | 30-second limit on the upload |
| Supabase unavailable, refused, or not configured | **503**, and **nothing is written**. The report keeps any photo it already had, and the report itself is unaffected |
| Rate limit (429) | Reported as "storage is busy" (503), with Supabase's `Retry-After` value when sent |
| Invalid file | 400 before any upload |

The mobile app treats a failed upload as its own state. For a report, it says "your report has
been filed, but the photo was not attached" and offers a retry. For a job, it says "the job has
not been completed yet" and offers a retry or completing without the photo.

**Data minimisation.** The storage bucket is public so the apps can display photos, so **all
metadata is removed before upload**: GPS location, camera make and model, comments and other
EXIF, XMP and IPTC data. The image is walked by its own file structure and not re-encoded, so
the pixels are unchanged. If a file cannot be fully parsed, it is **refused**, because nothing
could guarantee its location data had been removed.

**Evidence.** Verified live on 30 September 2026. A phone JPEG carrying GPS, a camera model and a
comment was stored with **none of that metadata** and identical pixels. A wrong service key
returned 503 and left the report unchanged, and the key did not appear in the log.

## 6.3 LLM provider

**Purpose.** Model inference for the five agents. Any **OpenAI-compatible** chat-completions
endpoint works. Changing provider (for example, from OpenRouter to a local Ollama server) is a
configuration change only, because no provider-specific feature is used.

**Failure handling.** Every model call has a 30-second timeout. A reply that fails schema
validation is retried exactly once. After that, the agent returns a recorded **safe failure**
instead of an error. The API's call to the agent service has its own 360-second timeout, and a
failed run is marked `Failed` with the reason, so the workflow never hangs.

**Usage and cost.** Every reply's token counts, as the provider reports them, are stored with
the agent run (both attempts added together when a reply was retried). Nothing is estimated: a
provider that reports no usage leaves the value empty, never zero. The API turns tokens into an
**estimated cost** from a price per million tokens set in configuration, and shows both on the
Agent monitoring page. Because every report starts an agent run, each user may file at most 10
reports an hour, which caps what any one account can spend.

**Data minimisation.** Agents receive facts, not personal data. Tool results leave out
technicians' names, reporter ids and photo URLs. The agent service has no database credentials.

## 6.4 Summary against the specification (§11)

| Requirement | Google Calendar | Supabase Storage | LLM provider |
|---|---|---|---|
| Business purpose and user benefit | Repairs avoid lectures | Photos for diagnosis and as evidence | Agent reasoning over unstructured text |
| Routed through the backend | API only | API only (uploads) | Agent service only, behind the API |
| Credentials protected | Service-account key in user secrets / environment | Service-role key in user secrets / environment | API key in environment |
| Timeouts | 10 s | 30 s | 30 s per call, 360 s per run |
| Invalid responses and failures | Degraded result; cache kept | 503; nothing written | One retry, then safe failure |
| Rate limits | 429 and quota 403; `Retry-After` reported | 429; `Retry-After` reported | Treated as a failed call |
| Personal data minimised | Nothing personal sent | Photo metadata stripped | Fact-only tool results |
