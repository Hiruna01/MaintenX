# 7. Security Considerations

Security in MaintenX is layered: the API is the only public entry point, every request is
authenticated and authorised there, and the AI subsystem is fenced off so that a mistaken or
manipulated model cannot change anything on its own.

## 7.1 Authentication

- **JWT bearer tokens**, signed with a symmetric key (HMAC-SHA256). The key, issuer and audience
  come from configuration, and the API refuses to start with a key shorter than 32 bytes.
- **Validation:** issuer, audience, signature and lifetime are all checked, with zero clock skew,
  so expiry is exact.
- **Lifetime:** 12 hours. The token carries the user id, email, role and a random token id.
- **Passwords** are hashed with ASP.NET Core's `PasswordHasher` (salted PBKDF2) and never
  returned by any endpoint.
- **No refresh tokens, by design.** A refresh flow needs a token store, rotation, reuse detection
  and revocation, which is a separate feature. Instead, **every request re-checks the account**:
  that it still exists, is still active, and still holds the role in its token. A deactivated
  user or a changed role is therefore locked out on the next request, not when the token expires.
- **Login** returns the same answer for a wrong password as for a deactivated account, so it does
  not reveal which accounts exist.
- **Rate limiting.** Sign-in and registration are limited to 10 attempts a minute per client
  address, so passwords cannot be guessed at full speed and accounts cannot be created in bulk.
  Behind the hosting proxy the address is the one the proxy reports, so a client cannot dodge
  the limit by writing its own. A refused request gets **429** with a `Retry-After` header and a
  message saying when to try again.

## 7.2 Authorisation

- **Role-based policies**, one per role (Reporter, Technician, Facilities Manager, Admin),
  generated from the role enum. Roles are not a seniority ladder, so an Admin cannot approve a
  work order.
- **Secure by default:** a fallback policy makes every endpoint require sign-in unless it is
  explicitly marked anonymous. Only login, register, the health check and the agent tool router
  are anonymous, and a test pins that list.
- **401 vs 403:** no valid token is **401**. A valid token with the wrong role, or for someone
  else's record, is **403**.
- **Ownership checks in the services:** only the reporter may answer their questions or confirm
  their repair, and only the assigned technician may complete a job. A Reporter's lists are
  scoped to their own records *before* paging, so counts and page numbers cannot reveal anyone
  else's.
- **Registration cannot grant privileges.** Anyone can register, but always as a Reporter. Asking
  for any other role without an Admin's token is a 403.
- **Admin safety:** an Admin cannot deactivate their own account or change their own role, so an
  active Admin always exists.

## 7.3 Input validation and data integrity

- **Server-side validation** on every input DTO (required fields, lengths, ranges); invalid input
  is a 400. The clients validate too, but the API is the rule.
- **Input DTOs never carry an `Id`, a status or an owner.** A client cannot choose a record's id,
  file a report as someone else, or post a work order as already "approved".
- **Bounded clarification answers:** a yes/no answer must be exactly "Yes" or "No", a picker
  answer must be one of the stored options, and short text is at most 100 characters. A bound
  kept only by the clients would be one direct HTTP request away from a chat box.
- **Money is `decimal`**, and both the DTOs and database CHECK constraints refuse negative values.
- **Concurrency:** approval decisions claim the order with a conditional update, so two managers
  cannot both decide. Slot bookings run at `Serializable` isolation, so a technician cannot be
  double-booked.
- **File uploads:** type and size are checked, the file's signature must match its type, names are
  generated by the server, and metadata is stripped (Chapter 6).

## 7.4 Secrets and configuration

- **No secret is committed.** `.env` files and `appsettings.Development.json` are git-ignored.
  Locally, secrets come from `dotnet user-secrets`; when deployed, from environment variables.
  `.env.example` lists every key with an empty value.
- **The CI workflow needs no secrets.** The agent tests run in stub mode, and the test database
  is a throwaway container.
- **Each credential lives in one place:**

  | Credential | Held by |
  | --- | --- |
  | Database connection string | The API only |
  | Supabase service-role key | The API only |
  | Google service account | The API only |
  | LLM API key | The agent service only |

- **Nothing secret reaches a client.** The web app sees only `VITE_`-prefixed values (the API's
  URL), and the mobile app only a compile-time API URL.
- **Logs** record method, path, status and duration, **never request bodies**, so passwords never
  reach a log sink. Exception details are returned only in Development; production clients get a
  generic ProblemDetails response.

## 7.5 Client-side security

- **Mobile:** the token is stored in `flutter_secure_storage` (iOS Keychain or Android encrypted
  storage), never in plain `SharedPreferences`, which can be read on a rooted device or from a
  backup.
- **Web:** the token is cleared on any 401, and the user is sent to sign in again.
- **Both clients** talk only to the API, and route guards hide screens a role cannot use. These
  guards are usability; the API enforces every rule regardless.
- **Transport:** the API redirects HTTP to HTTPS, and CORS allows only the configured web origin.

## 7.6 Agentic AI security

| Control | How it is enforced |
|---|---|
| **No database access** | The agent service has no connection string at all. It reads data only through API tools |
| **Authenticated in both directions** | API ↔ agent calls carry a shared secret, compared in constant time. A missing secret is a 401 before the request body is read |
| **Allow-listed tools** | Seven read-only tools in a **hardcoded C# dictionary**. Nothing a model outputs can add, rename or describe a capability. Unknown tools are refused and logged in the audit trail |
| **Least privilege** | Each agent has its own tool subset. No tool approves, raises or changes a work order |
| **Validated tool input** | Tools accept only a validated id. Row limits are fixed in the API, not chosen by the caller |
| **Ended runs** | A workflow that has failed or closed accepts no more tool calls (409) |
| **Output validation** | Strict schemas with unknown fields rejected. No schema has an "approved" or free-text message field |
| **Prompt-injection defence** | User-typed text reaches the model only as one JSON-encoded data block it cannot break out of, and the prompt says it is data. Stored text the agents fetch through tools, such as technicians' notes, is fenced the same way. Tested for every agent, and measured in live evaluations: 9 injection cases, including 3 hidden inside tool results, each run 5 times, 45 / 45 resisted |
| **Cost budget** | Filing a report starts an agent run, so each user may file at most 10 reports an hour. The 11th is refused with 429 and nothing is written |
| **Decisions stay in C#** | Approval, cost limits and state changes are deterministic code or human actions. The strategist is never told the approval threshold |
| **Timeouts and retry limits** | 30 s per model call, one retry, then a safe failure. 360 s per agent run. At most 3 attempts per verification check |
| **Safe failure** | Failures are recorded on the workflow, never as a crash or a hanging run |
| **Auditability** | Every agent run, tool call and approval decision is stored and visible to managers |
| **No chat interface** | Agents run one round per call, with no conversation history, so there is no free-text channel to manipulate them through |

## 7.7 Known limitations

- **Rate limits are per address and per user, not per account.** An attacker with many addresses
  could still try one account's password many times. Locking an account after repeated failures
  would close this, at the cost of letting anyone lock someone else out.
- **A poisoned note is not flagged.** In the evaluations the model never followed an instruction
  hidden in a technician's note, and no agent could act on one anyway, but it never mentioned the
  instruction either. Nothing alerts a person that stored data contains an injection attempt.
- **The web token is stored in `localStorage`.** It is simple and works with the session-expiry
  design, but it would be readable by any script injected through an XSS flaw. React's output
  escaping lowers that risk; an `HttpOnly` cookie would remove it.
- **Photos are in a public bucket.** Object names are random GUIDs and all metadata is stripped,
  but anyone holding a URL can view the photo. Signed URLs would remove this.
- **One shared secret** is used for both directions between the API and the agent service.
